### 7.5 没有测试框架的 GUI 应用怎么验
Electron / 浏览器类项目常常没有测试框架，但不等于只能靠手点：

- 以 `--remote-debugging-port=9222` 启动，用 Node 全局 `WebSocket` 直连 CDP，**在真窗口上驱动真实 UI 与 IPC**（派发真事件、读真实状态，不是模拟）。
- `Runtime.evaluate` 带 `awaitPromise` 可等异步；**`Runtime.exceptionThrown` 抓页面加载期异常**——这是唯一能看到子窗口报错的途径（渲染进程的 console 不会转发到主进程日志）。曾靠它定位到「动态生成的元素被提前绑监听器 → null 抛错 → 整段脚本静默中断」。
- `Page.captureScreenshot` 拿应用外观；`desktopCapturer` 拿桌面合成结果。**窗口层效果（`setOpacity`、层级）只有后者能验**，网页截图看不到。
- **系统文件对话框没法自动化** → 把「选文件」和「处理文件」拆成两个函数，处理函数接受显式路径参数，测试直接传路径跳过对话框。这个拆分本身也更清楚，值得主动做。
- 动画/动效量 `getBoundingClientRect()` / `getComputedStyle()`，它们反映的是动画进行中的实际值（能验「原点在底边所以缩放时底边不动」这种性质）。

### 7.6 性能问题怎么查（2026-09-16 桌面挂件 CPU/内存优化）

用户说「占用有点多」时，**先量再猜**。本次三个听起来都合理的假设里，**前两个被实测推翻**，真凶是第三个。

- **判读内存看「私有内存」，不看工作集。** Chromium 做大量进程间共享映射，工作集能虚高十倍：本项目音频服务工作集 **230MB**、私有只有 **10.3MB**；真正吃内存的是另一个 node 子进程（私有 **384MB**）。只按任务管理器判读会把优化方向整个搞反。Windows 上用 `Get-Process` 的 `PrivateMemorySize64`。
- **量整棵进程树，别只看一个进程。** 改完先看 GPU 进程：40.9% → 0.17%，差点直接下「16 倍优化」的结论。**改测整棵树是为了确认另一件事——工作有没有被挪到别的进程去。** 本例确实没挪（渲染进程 0.27%），但这一步不能省。
- **采样窗口必须覆盖现象的周期。** 同一个进程：25 秒窗口测出 0.06%、75 秒测出 8.56%、130 秒测出 38.6%。被观测的现象有 60 秒周期，窗口短于周期就必然得出互相矛盾的数字。**先找周期（定时器/刷新间隔），窗口取它的整数倍。**
- **常驻 node 进程的内存只涨不落。** V8 的堆高水位**不归还操作系统**：冷启动全量扫描后冲到 384MB，之后盯 40 秒纹丝不动、CPU 零增长。**这不是泄漏**（泄漏会持续涨，且重启后从零开始涨），是死掉的高水位。**唯一真正释放的办法是让进程死一次**——加定期 `process.exit(约定退出码)` 由父进程重新拉起。退出码要和崩溃区分开，否则日志被污染、下次真崩了看不出来。
- **优化前先证伪，别停在第一个合理解释上。** 本例真凶是 `will-change: transform` 撞上祖先的 `preserve-3d`：图层被提升进 3D 上下文，每帧都要在 3D 空间重新光栅化（约 30ms/帧，一张 104×92 的图吃掉近一整个核心）。「听起来合理」和「实测是它」之间差一次 A/B。
- **连续性本身有非线性代价。** 同一个动画：连续跑 21.07%，每分钟只跑 12.6 秒 2.48% —— 占空比差 4.8 倍，CPU 差 **43 倍**。让合成器有机会 idle，比单纯减少工作量值钱得多。
- **`JSON.stringify(x).length` 是纯浪费的隐性开销。** 它不为数据服务只为量长度，却走完整序列化路径。要判大小就复用真正写盘那次的结果。
- **不收敛的阈值裁剪比不裁剪更危险。** 「超过 40MB 就把每文件记录截到 800 条」——截完 155 文件 × 800 条 ≈ 65MB **仍超阈值**，而判据 `records.length > 800` 已为 false 不再触发，**永远卡在超标状态**。阈值保护必须验证「裁剪后确实低于阈值」，用逐轮折半之类的收敛算法。

### 只有成品、没有源 —— 反推重建怎么做（2026-10-01 推免材料 PDF）

多设备接力的常见局面：手机（Operit）做完一段成品，电脑端接手时**源文件拿不到，只有一份排好版的 PDF**。不用去要源文件，成品本身就能当源用：

- **反推四件套**（PyMuPDF）：① 逐 span 抽文字 + 字号 + 字体（层级直接还原：17 / 13.5 / 12 / 11.5 / 9.5 / 8.4）；② `extract_image` 按页抠内嵌图；③ `get_drawings` 数分隔线 / 图框——「每个大节前一条通栏细线、每图一个灰框」= 8 线 + 3 框，重建后数量必须对齐；④ 页脚样式（文案、字号、首页不显）。
- **重建后必过逐字回归**：两份 PDF 全文去空白比对（正则先剥页脚），IDENTICAL 才放行。这个断言专抓「内容符号被当标记吃掉」这类静默丢失——本项目一次抓到 13 个「→」被吃。
- **重建 = 内容不动的重排版**：字体可以换（Droid → 微软雅黑），字号体系、图片限高、边距、页脚文案照抄参数表。
- **中文 PDF 排版有现成编译器**：`Desktop\ai项目\scripts\build_pdf.py`（内容源标记 + 自实现禁则换行 + 编译断言 + 字距两端对齐），做文档直接改 `content/*.txt` 重编译——别从零写 fpdf2，三个坑见踩坑池。
- **截图素材优先级**：用户真机手截 > 自己无头渲染（参数坑见踩坑池）。**上版前先物检边缘**：任务栏、悬浮挂件残影、浏览器框、滚动条——本项目两张深色截图都蹭进了置顶挂件的一角，先裁再放。
- **内容与排版分离的组织方式**：`content/` 一节一个 txt → 编译器一次出全册 → 出片后自动跑哨兵（禁词 / 关键事实 / 口径词）。改一句话不碰排版，一分钟出新版。
